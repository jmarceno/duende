Overview

Duende supports importing other source files as modules. Each .du file is a module, and the module name is the file path from the project root without extension, using dots as separators. For example, examples/modules/testModule.du has the module name modules.testModule.

Basic import

import modules.testModule

int main() do
    print(testModule.add(1,2))
end

By default, importing a module provides a short alias equal to the last path segment (here testModule). Use that to qualify functions and types from the module.

Selective import

import modules.otherModule { subtract }

int main() do
    print(subtract(2,4))
end

You can import a subset of symbols. Internally the compiler creates aliases so names appear directly in the current file.

Aliases

import modules.testModule as TM
import modules.otherModule { subtract as minus }

int main() do
    print(TM.add(1,2))
    print(minus(2,4))
end

Relative imports

Inside a module the compiler resolves bare names relative to the current module's parent. For example from modules/testModule.du you can write:

import otherModule

This is resolved to modules.otherModule if such module exists.

Re-exports and visibility

public import modules.testModule
private import modules.otherModule { subtract }

public import re-exports the imported module's alias, so importers of this module can reach that module's public symbols through the alias. private import keeps the alias in the current module (the default). A later module that imports this one does not see a private import, and using one of its symbols is a compile error.

Wildcards

Writing import some.module.* expands to import all exported symbols, including module-level variables, from that module (resolved statically at compile time).

Typed interfaces

Each module has a public interface. Functions, variables, structs, frames, enums, and protocols in the module are visible to importers with their declared types. A type you define belongs to that module: Point in shapes.left and Point in shapes.right are different types, even when the fields match. list, dict, Result, and Maybe are the same types in every module. Nested arguments are kept, so list<list<int>> imported from another module is still a list of int lists.

Parameter names and default values are part of an imported function. Calls can use those names and can omit parameters that have defaults. A call through a module name, a selective import, a wildcard import, or a public import re-export uses that same signature. The compiler rejects an unknown name, the same name twice, too many arguments, a missing argument, and a nested list, dict, Result, or Maybe value of the wrong type. Ok, Error, Some, and None take the type of the parameter they are passed to. Supplied arguments run once, from left to right in the order they are written; defaults for omitted parameters run after them. Assigning to an imported let is rejected. Assigning a value of the wrong type, or passing one to an imported function, is rejected.

let auto and var auto exports take their type from the initializer when that type follows from declared types. If two modules import each other and each auto binding depends on the other, inference cannot choose a type. Declare the type on the binding. The compiler reports that error and does not treat the binding as an unknown type.

Notes

  • Imports are resolved relative to the project root and the current module.
  • Circular imports are supported; the compiler builds a module graph and generates each module once.
  • Standard library is reserved under the std prefix.
  • Math functions require import std.math in each module that uses them.
  • Built-in providers: the Duende compiler embeds a small set of provider manifests (for example: terminal, std.csv, std.json) so these modules are available out of the box. If a provider declares external dependencies (e.g. a dub package), the compiler will automatically build your program via dub when needed — no manual setup required beyond having a D toolchain and dub installed.
  • Additional providers: you can still add your own by placing a duende_packages folder next to the duende executable with provider manifests. The compiler will load these in addition to the built-ins.
